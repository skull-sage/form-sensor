# Form Sensor Module - Requirements Document

## Module Overview

The Form Sensor module provides semantic text similarity detection for form field validation. It uses sentence transformers to detect whether provided text descriptions match predefined descriptions contextually using the all-MiniLM-L6-v2 model. This enables applications like smart form validation, content moderation, FAQ matching, and duplicate detection.

## Glossary

- **Form_Sensor**: The core module that processes text descriptions and determines semantic similarity for form validation
- **Sentence_Transformer**: The all-MiniLM-L6-v2 model used for generating text embeddings
- **Text_Sensor**: A collection of paragraphs mapped to a specific nameId for semantic comparison
- **NameId**: Unique identifier for a text sensor containing multiple paragraph descriptions
- **Similarity_Score**: A numerical value (0-1) representing how semantically similar two text descriptions are
- **Similarity_Threshold**: A configurable minimum similarity score required for a match (default: 0.6)
- **Text_Embedding**: Vector representation of text generated by the sentence transformer model
- **Cosine_Similarity**: Mathematical method used to calculate similarity between text embeddings
- **Paragraph_Splitting**: Process of dividing multi-paragraph text into individual paragraph descriptions

## Requirements

### Requirement 1

**User Story:** As a system administrator, I want to create text sensors from multi-paragraph text, so that I can establish reference libraries for semantic comparison.

#### Acceptance Criteria

1. WHEN an administrator calls POST /form-sensor/create-text-sensor/:nameId with {"text": "variable number of paragraphs separated by newlines"}, THE Form_Sensor SHALL split the text by newlines into individual paragraphs
2. WHEN text is split into paragraphs, THE Form_Sensor SHALL create a mapping where key is nameId and value is an array of paragraphs regardless of the number of paragraphs
3. WHEN paragraphs are stored, THE Form_Sensor SHALL generate embeddings for each paragraph using the all-MiniLM-L6-v2 model
4. WHEN embeddings are generated, THE Form_Sensor SHALL maintain a parallel mapping where key is nameId and value is an array of embeddings corresponding to each paragraph
5. WHEN a nameId already exists, THE Form_Sensor SHALL replace both the paragraph mapping and embedding mapping with new data

### Requirement 2

**User Story:** As a user, I want to check semantic similarity against a specific text sensor, so that I can determine if my text matches any stored paragraphs.

#### Acceptance Criteria

1. WHEN a user calls POST /form-sensor/text-sensor/:nameId with {"text": "a description"}, THE Form_Sensor SHALL generate an embedding for the input text using all-MiniLM-L6-v2
2. WHEN calculating similarity, THE Form_Sensor SHALL compare the input text embedding against all paragraph embeddings stored under the specified nameId
3. WHEN similarity scores are calculated, THE Form_Sensor SHALL use cosine similarity between the input embedding and each paragraph embedding
4. WHEN similarity scores are calculated, THE Form_Sensor SHALL return {"confidence_score": score, "matched_paragraph": "text"} with the highest similarity score regardless of threshold

### Requirement 3

**User Story:** As a system operator, I want consistent similarity threshold behavior, so that text sensor matching is predictable and reliable.

#### Acceptance Criteria

1. WHEN checking text similarity, THE Form_Sensor SHALL use a reference threshold of 0.6 for frontend guidance
2. WHEN similarity scores are >= 0.6, THE Form_Sensor SHALL consider the text as matching and return the confidence score
3. WHEN similarity scores are < 0.6, THE Form_Sensor SHALL still return the actual confidence score for frontend guidance
4. WHEN multiple paragraphs exceed the 0.6 threshold, THE Form_Sensor SHALL return the highest confidence score among all matches
5. WHEN calculating confidence scores, THE Form_Sensor SHALL return the actual cosine similarity value (not a boolean)

### Requirement 4

**User Story:** As a developer, I want specific RESTful API endpoints for text sensor operations, so that I can integrate semantic similarity checking into other applications.

#### Acceptance Criteria

1. WHEN the API receives a GET request to the root endpoint, THE Form_Sensor SHALL return a health check response
2. WHEN the API receives a POST request to /form-sensor/create-text-sensor/:nameId, THE Form_Sensor SHALL process the text and create paragraph-based sensors
3. WHEN the API receives a POST request to /form-sensor/text-sensor/:nameId, THE Form_Sensor SHALL check similarity against the specified sensor
4. WHEN the API receives a GET request to /form-sensor/text-sensors, THE Form_Sensor SHALL return all available text sensor nameIds
5. WHEN the API receives a DELETE request to /form-sensor/text-sensor/:nameId, THE Form_Sensor SHALL remove the specified text sensor

### Requirement 5

**User Story:** As a user, I want a web interface to interact with the semantic sensor, so that I can easily manage descriptions and check similarities without using API directly.

#### Acceptance Criteria

1. WHEN a user accesses the web interface, THE Form_Sensor SHALL display forms for adding text sensors and checking similarity
2. WHEN a user adds a text sensor through the interface, THE Form_Sensor SHALL validate input and provide visual feedback
3. WHEN a user submits text for similarity checking, THE Form_Sensor SHALL display results with similarity percentages and color coding
4. WHEN similarity results are displayed, THE Form_Sensor SHALL show the confidence score and matched paragraph
5. WHEN confidence scores are displayed, THE Form_Sensor SHALL use color coding (green ≥80%, orange ≥60%, amber ≥40%, red <40%)

### Requirement 6

**User Story:** As a system operator, I want proper error handling and validation, so that the system provides clear feedback and maintains stability.

#### Acceptance Criteria

1. WHEN invalid input is provided, THE Form_Sensor SHALL return descriptive error messages with HTTP status codes
2. WHEN the sentence transformer model fails to load, THE Form_Sensor SHALL return a service unavailable error
3. WHEN network requests fail, THE Form_Sensor SHALL provide appropriate timeout and retry mechanisms
4. WHEN empty or malformed text is submitted, THE Form_Sensor SHALL validate input and return specific error messages
5. WHEN system resources are insufficient, THE Form_Sensor SHALL handle gracefully and return resource limitation errors

### Requirement 7

**User Story:** As a developer, I want proper CORS configuration, so that the frontend can communicate with the backend API from different origins.

#### Acceptance Criteria

1. WHEN the frontend makes requests from localhost:8080, THE Form_Sensor SHALL accept and process the requests
2. WHEN preflight OPTIONS requests are made, THE Form_Sensor SHALL respond with appropriate CORS headers
3. WHEN credentials are included in requests, THE Form_Sensor SHALL handle them according to CORS policy
4. WHEN unauthorized origins attempt access, THE Form_Sensor SHALL reject requests with appropriate error responses
5. WHEN API responses are sent, THE Form_Sensor SHALL include necessary CORS headers for browser compatibility
